## ۱. خلاصهٔ اجرایی

Gym4Me یک پلتفرم چندنقشی ورزش برای بازار ایران است که چهار جریان را در یک اکوسیستم به هم متصل می‌کند:

1. کشف و رزرو انواع خدمات ورزشی؛ از باشگاه بدنسازی و کلاس تا استخر، زمین فوتبال و جلسهٔ خصوصی مربی.
2. خرید، پرداخت، حضور، عضویت و تمدید؛ به‌صورت آنلاین یا با کمک پذیرش باشگاه.
3. مربیگری، برنامهٔ تمرینی، ثبت اجرای تمرین، ارتباط مربی و شاگرد و پایش پیشرفت.
4. مدیریت عملیاتی و مالی باشگاه برای مالک، پرسنل و ادمین پلتفرم.

قابلیت جدید محوری این PRD، **دفترچهٔ روزانهٔ ورزش و سلامت ورزشکار** است: ثبت آب، قدم، پیاده‌روی، وزن، خواب، رکوردهای ورزشی و لاگ دقیق تمرین؛ با امکان اتصال اختیاری به Apple Health و Health Connect و اشتراک کنترل‌شده با مربی.

در کنار محصول، باید یک لایهٔ **Dynamic Delivery** ساخته شود تا قابلیت‌هایی که از قبل در اپ نصب شده‌اند با Remote Config و Feature Flag به‌تدریج فعال شوند. نسخهٔ اپ، build بومی، نسخهٔ API و نسخهٔ manifest چهار مفهوم جدا هستند. `/api/v2` فقط برای تغییرات ناسازگار قرارداد API ایجاد می‌شود؛ روشن‌کردن یک فیچر دلیل ساخت API جدید نیست.

## ۲. مسئله و فرصت

### مسئله‌های ورزشکار

- رزرو باشگاه، کلاس، مربی، زمین و استخر پراکنده و عمدتاً تلفنی/پیامی است.
- خرید خدمت از سابقهٔ حضور، برنامهٔ مربی و پیشرفت واقعی ورزشکار جداست.
- وزن، رکورد، آب، خواب و تمرین در اپ‌ها یا دفترهای مختلف ثبت می‌شوند.
- کنترل دسترسی مربی به دادهٔ سلامت معمولاً شفاف و جزئی نیست.
- در اینترنت ضعیف، برنامه و سوابق ضروری نباید کاملاً از دسترس خارج شوند.

### مسئله‌های مربی

- دریافت هزینه، ارسال برنامه، پیگیری پایبندی و ارتباط با شاگرد بین پیام‌رسان، فایل و دفتر پخش است.
- مربی دید یکپارچه‌ای از اجرای برنامه، رکوردها، روند وزن و محدودیت‌های سلامت ندارد.
- نسخه‌بندی برنامه و سابقهٔ تغییرات ضعیف است و اختلاف دربارهٔ برنامه یا جلسه به‌سختی حل می‌شود.

### مسئله‌های باشگاه

- رزرو، عضویت، صندوق، بدهی، حضور، ظرفیت، تسویه و پیام‌رسانی ابزارهای جدا دارند.
- پذیرش باید بتواند برای فرد بدون اپ فروش، رزرو، تمدید و check-in انجام دهد.
- مدل یک محصول باید هم بدنسازی و کلاس و هم استخر، فوتبال و سایر منابع را بدون ساخت سامانه‌های جدا پوشش دهد.

### فرصت بازار

بررسی نمونه‌های فعلی نشان می‌دهد بازار بین چند دسته راهکار تقسیم شده است:

- [ایران بدن](https://app.iranbadan.com/fa/) و [مربی‌ها](https://morabiha.com/) بر برنامهٔ مربی، شاگرد و پایش پیشرفت تمرکز دارند.
- [ورزشکار](https://varzeshkar.com/) رزرو، مربی، برنامه و تغذیه را به‌عنوان پلتفرم جامع معرفی می‌کند.
- [پاکوب](https://pakoobapp.ir/) رزرو، پرداخت، اعلان و عملیات تیم/باشگاه را پوشش می‌دهد.
- [اتوماسیون باشگاه تایگر](https://tigerteco.com/club-automation) بر عضویت، تردد، رزرو سانس و عملیات مجموعه تمرکز دارد.

**استنباط محصول:** مزیت Gym4Me صرفاً زیادبودن فیچر نیست؛ مزیت قابل‌دفاع، اتصال end-to-end «کشف و خرید → حضور → مربیگری و پایش → مراجعهٔ مجدد → تمدید» در یک حساب چندنقشی و با نیازهای مالی/عملیاتی ایران است.

## ۳. چشم‌انداز و جایگاه محصول

> Gym4Me باید سیستم عامل روزمرهٔ ورزش در ایران باشد: یک اپ برای ورزشکار و مربی/مالک، یک پنل برای عملیات، و یک منبع حقیقت برای رزرو، پول، حضور، برنامه و پیشرفت.

### اصول محصول

- **حلقهٔ اصلی قبل از عمق جانبی:** عضویت یا رزرو → پرداخت → حضور → مراجعهٔ مجدد → تمدید.
- **یک مدل عمومی برای انواع ورزش:** تفاوت استخر، فوتبال، کلاس و بدنسازی تا حد امکان با resource، attribute و policy پیکربندی شود.
- **اعتماد قبل از رشد:** قیمت، لغو، حریم خصوصی، تأیید مربی و سوابق مالی شفاف باشند.
- **عملیات ایران‌محور:** شمسی، هفتهٔ شنبه‌محور، IRR/IRT، پرداخت حضوری، SMS و شبکهٔ ضعیف از ابتدا دیده شوند.
- **دادهٔ سلامت تحت کنترل ورزشکار:** پیش‌فرض خصوصی، رضایت قابل لغو و اشتراک حداقلی.
- **فعال‌سازی تدریجی:** قابلیت آماده به‌صورت cohort یا per-platform فعال شود؛ Feature Flag جای مجوز امنیتی را نمی‌گیرد.

## ۵. اهداف و خارج از محدوده

### اهداف محصول

- تکمیل جریان واقعی رزرو و عضویت تا حضور و Ledger.
- تبدیل برنامهٔ مربی به تجربهٔ اجرایی قابل ثبت، نه فایل قابل مشاهده.
- ایجاد دفترچهٔ روزانهٔ خصوصی ورزشکار و نمودار روند.
- امکان اشتراک انتخابی داده با مربی و قطع فوری دسترسی.
- فعال‌سازی تدریجی فیچرهای از پیش نصب‌شده بدون انتشار اجباری برای هر تغییر تنظیمی.
- سازگاری هم‌زمان حداقل دو نسل API در زمان مهاجرت ناسازگار.
- فراهم‌کردن عملیات حضوری برای اعضایی که اپ ندارند.

### خارج از محدودهٔ این PRD

- جایگزینی تشخیص یا توصیهٔ پزشکی؛ Gym4Me ابزار ثبت و مربیگری است، نه سامانهٔ درمان.
- تضمین «هیچ‌وقت نیاز به آپدیت اپ نیست». تغییر plugin، permission یا کد بومی به نسخهٔ مارکت نیاز دارد.
- مهاجرت از MongoDB یا جایگزینی Capacitor/Next.js با Expo.
- ساخت مدل دامنهٔ جدا برای تک‌تک رشته‌ها پیش از شکست مدل resource/policy مشترک.
- هوش مصنوعی خودمختار برای تجویز تمرین یا تغذیه در فاز نخست.

## ۶. تصویر وضعیت فعلی

### نقاط قوت موجود

- مونوریپو با `apps/api`، `apps/mobile`، `apps/admin`، `apps/website` و پکیج‌های مشترک.
- اپ موبایل فعلی بر Next.js static export + Capacitor بنا شده و باید حفظ شود.
- احراز هویت چندنقشی و `activeRole`، پروفایل‌ها، KYC و بخش بزرگی از عملیات باشگاه وجود دارد.
- URI versioning برای API فعال است و مسیر پیش‌فرض `/api/v1` است.
- مدل‌های `WorkoutPlan`، `WorkoutLog`، `ProgressMetric`، `MetricType`، `PersonalRecord` و `ProgressPhoto` وجود دارند.
- حریم متریک/عکس/برنامه در مدل پیش‌فرض `PRIVATE` است.
- APIهای متریک، رکورد شخصی و لاگ تمرین وجود دارند، اما تجربهٔ کامل end-to-end هنوز بسته نشده است.

### مواردی که باید تقویت یا اصلاح شوند

| لاگ تمرین | مدل ست/تکرار/RPE وجود دارد، اما اجرای جلسه کامل نیست | فرم اجرای تمرین، draft، resume، اصلاح و sync | P0 |

### قابلیت‌های واقعاً جدید

- ثبت آب، قدم، مسافت و مدت پیاده‌روی، مدت و کیفیت خواب و انرژی/خستگی.
- هدف، streak و reminder قابل تنظیم بدون ایجاد فشار ناسالم.
- همگام‌سازی idempotent Apple Health و Health Connect.
- grant جزئی داده به مربی.
- خلاصهٔ روزانه/هفتگی و insight غیرپزشکی.
- bootstrap عمومی اپ، Feature Flag، rollout درصدی، min-version و kill switch.
- پنل مدیریت انتشار و audit تغییرات فیچر.

## ۷. محدودهٔ قابلیت‌ها بر اساس محصول

### ۷.۱ ورزشکار

#### P0 — هستهٔ تراکنش و استفادهٔ روزانه

- کشف باشگاه، مربی، کلاس، استخر، زمین و سانس با فیلترهای ایران‌محور.
- رزرو تکی/دوره‌ای/چندنفره و مشاهدهٔ قیمت و سیاست لغو پیش از پرداخت.
- پرداخت، کیف پول، فاکتور، لغو، بازپرداخت، waitlist و check-in.
- خرید و تمدید عضویت، اعتبار جلسه/ورود، فریز و درخواست انتقال.
- مشاهدهٔ برنامهٔ مربی و ثبت اجرای جلسه با ست، تکرار، وزن، RPE، درد و یادداشت.
- ثبت روزانهٔ وزن، آب، قدم، پیاده‌روی، خواب و رکورد شخصی.
- تاریخچه و نمودار واقعی با حریم پیش‌فرض خصوصی.
- پیام با مربی و اشتراک انتخابی متریک‌ها.

#### P1 — نگهداشت و کیفیت تجربه

- هدف، reminder، streak انعطاف‌پذیر و خلاصهٔ هفتگی.
- اتصال Health Connect/Apple Health و حل تعارض دادهٔ دستی/دستگاه.
- عکس پیشرفت، اندازه‌های بدن و مقایسهٔ بازه‌ها.
- دسترسی محدود آفلاین به برنامه و صف ثبت تمرین/متریک.
- export و حذف داده، تاریخچهٔ رضایت و مشاهدهٔ دسترسی‌های فعال.
- ویدئوی اجرای حرکت و بازخورد مربی.

#### P2 — پس از اثبات retention

- challenge اجتماعی کنترل‌شده، گروه تمرینی و leaderboard اختیاری.
- insight پیش‌بینی‌گر غیرپزشکی با توضیح منبع داده.
- یکپارچگی ساعت/پوشیدنی بیشتر و auto-detection تمرین.

### ۷.۲ مربی

#### P0

- پروفایل حرفه‌ای و تأیید مدرک؛ خدمت حضوری/آنلاین/در منزل.
- تقویم، buffer، چند محل، بستهٔ جلسه و جلوگیری از تداخل.
- بانک حرکت، template، برنامهٔ ساختاریافته و اختصاص به شاگرد.
- مشاهدهٔ اجرای برنامه و متریک‌هایی که ورزشکار صریحاً اجازه داده است.
- بازخورد متنی، اصلاح برنامه با نسخهٔ جدید و تاریخچهٔ تغییر.
- پیام، حضور، تأخیر، no-show و لغو اضطراری.

#### P1

- گروه‌بندی شاگرد، cohort، پایبندی و هشدار افت مشارکت.
- ویدئوی فرم حرکت، برنامهٔ جایگزین و یادداشت محرمانه.
- درآمد، سهم هر جلسه، کسورات، تسویه و اعتراض.
- CRM لید از اولین تماس تا trial و تبدیل.

### ۷.۳ مالک و پرسنل باشگاه

#### P0

- باشگاه/شعبه/فضا/کلاس/سانس/ظرفیت و سیاست جنسیت/سن/سطح.
- فروش حضوری عضویت بدون الزام اپ؛ نقد، POS، کارت‌به‌کارت و ترکیبی.
- عضو/مهمان، بدهی، پرداخت جزئی، تمدید، فریز، check-in و رسید.
- رزرو تلفنی/حضوری، waitlist و جابه‌جایی مربی/فضا/سانس.
- پرسنل با مجوز per-member، نه صرفاً عنوان شغلی.
- گزارش روزانهٔ فروش، حضور، ظرفیت و اعضای در معرض ریزش.

#### P1

- صندوق شیفت، اقساط، پورسانت، تسویه و خروجی حسابداری.
- چندشعبه‌ای، سازمانی/خانوادگی، تجهیزات، کمد و تعمیرات.
- lifecycle تمدید/عدم مراجعه با رضایت کانال و frequency cap.

### ۷.۴ ادمین پلتفرم

#### P0

- مدیریت کاربران، نقش‌ها، KYC، باشگاه و مربی.
- کاتالوگ رشته، امکانات، حرکت، MetricType و خدمات.
- AuditLog، dispute، refund، کمیسیون و سلامت providerها.
- مدیریت Feature Flag، rollout، release policy و حداقل نسخه.
- kill switch برای فیچر پرریسک بدون خاموش‌کردن کل اپ.

#### P1

- داشبورد funnel، عرضه، رزرو، پرداخت، retention و rollout.
- A/B و holdout با assignment پایدار.
- CMS، FAQ، قالب اعلان، moderation و پشتیبانی.

### قواعد دادهٔ متریک

- ذخیرهٔ زمان در UTC؛ نمایش با timezone ایران و تقویم شمسی.
- واحد canonical در API؛ تبدیل واحد فقط در لایهٔ نمایش.
- دادهٔ دستی و دستگاه هر دو sample هستند و `source` مشخص دارند.
- دادهٔ provider با `sourceRecordId` یا idempotency key تکراری نمی‌شود.
- متریک بازه‌ای مثل خواب `period.start/end` دارد؛ مقدار تجمیعی بدون بازه مبهم نباشد.
- کیفیت خواب عدد ۱ تا ۵ و label محلی دارد؛ جایگزین مدت خواب نیست.
- خلاصهٔ روزانه derived است و منبع حقیقت sampleهای خام باقی می‌مانند.
- دادهٔ سلامت نباید بدون consent وارد تبلیغات یا segmentation رشد شود.

## ۱۰. جریان‌های UX کلیدی

### ثبت سریع روزانه

1. ورزشکار از خانه یا صفحهٔ متریک «ثبت فعالیت» را می‌زند.
2. نوع متریک، مقدار، زمان و یادداشت اختیاری را وارد می‌کند.
3. UI واحد و بازهٔ معتبر را نشان می‌دهد.
4. در شبکهٔ ضعیف رکورد locally pending می‌شود و client id می‌گیرد.
5. sync موفق، مقدار جدید را در تاریخچه و خلاصهٔ همان روز نمایش می‌دهد.

### اجرای جلسهٔ تمرین

1. ورزشکار جلسهٔ امروز را باز و «شروع تمرین» می‌زند.
2. app draft محلی/سروری می‌سازد و در خروج ناخواسته از بین نمی‌رود.
3. هر ست با تکرار، وزن و RPE ثبت؛ timer استراحت اختیاری است.
4. پایان جلسه خلاصه و رکوردهای احتمالی را نشان می‌دهد.
5. ورزشکار completion را تأیید می‌کند؛ مربی فقط طبق grant می‌بیند.

### اشتراک با مربی

1. ورزشکار مربی فعال و scopeها را انتخاب می‌کند: تمرین، وزن، خواب یا عکس.
2. اپ هدف، مدت و اثر اشتراک را واضح توضیح می‌دهد.
3. grant زمان‌دار ایجاد می‌شود و در تنظیمات قابل مشاهده است.
4. قطع رابطه یا revoke، دسترسی query-time را فوراً می‌بندد.
5. سوابق دسترسی حساس در AuditLog باقی می‌ماند.

### فعال‌سازی تدریجی فیچر

1. ادمین flag را برای beta و ۵٪ Android فعال می‌کند.
2. cohort بر اساس installation id ثابت می‌ماند.
3. exposure و error rate ثبت می‌شوند.
4. rollout تا ۲۵٪، ۵۰٪ و ۱۰۰٪ افزایش می‌یابد.
5. عبور از guardrail، kill switch/rollback را فعال می‌کند.

## ۱۱. خطاها و recoveryهای اجباری

- ارسال دوبارهٔ متریک/لاگ پس از timeout نباید رکورد دوم بسازد.
- تعارض دادهٔ دستی و دستگاه حذف خودکار ایجاد نمی‌کند؛ sourceها حفظ می‌شوند و policy خلاصه مشخص است.
- revoke مربی حتی با token قدیمی در query-time اعمال می‌شود.
- manifest نامعتبر نادیده گرفته و آخرین config سالم استفاده می‌شود.
- نبود bootstrap نباید login یا فلوهای ضروری را بی‌دلیل قفل کند؛ فقط فیچرهای پرریسک fail-closed هستند.
- minimum version فقط وقتی اجباری شود که نسخهٔ قدیمی ناسازگار یا ناامن است.
- شکست provider سلامت، دادهٔ دستی را مختل نمی‌کند.
- حذف حساب/داده باید تکلیف عکس، sample خام، aggregate، audit و دادهٔ مالی غیرقابل‌حذف را جدا کند.

## ۱۲. KPI و ابزار اندازه‌گیری

### North Star پیشنهادی

`Weekly Successful Active Athletes`: ورزشکاری که در هفته حداقل یک رزرو/حضور یا جلسهٔ تمرین کامل دارد و اقدام پیگیری مانند ثبت متریک یا برنامه را انجام می‌دهد.

### KPIهای محصول

| حوزه | KPI |
|---|---|
| رزرو | search→detail، detail→booking، payment success، check-in rate |
| عضویت | activation، visits/member، renewal، freeze/churn |
| مربیگری | plan assignment، session completion، coach feedback latency |
| tracking | first log، weekly logging athlete، 4-week retention، sync success |
| اعتماد | cancellation dispute، refund time، privacy revoke success |
| باشگاه | desk sale time، check-in latency، debt recovery، occupancy |
| delivery | flag exposure، error/crash per cohort، bootstrap availability، forced-update rate |

### Guardrailها

- افزایش crash/error پس از exposure.
- ثبت تکراری متریک یا تراکنش.
- افزایش درخواست پشتیبانی/ابهام privacy.
- notification opt-out و reminder fatigue.
- اختلاف cohort یا فعال‌شدن flag خارج از platform/version مجاز.

## ۱۵. تصمیم‌های باز برای تأیید

1. آیا bootstrap نسخه‌خنثی در `/api/app-config/bootstrap` باشد؟ پیشنهاد: بله، با `schemaVersion` مستقل.
2. آیا v1 و v2 حداقل شش ماه هم‌زمان پشتیبانی شوند؟ پیشنهاد: بله، مگر رخداد امنیتی.
3. fail-safe هر flag چیست؟ پیشنهاد: فلوهای خرید/ورود fail-open روی آخرین config سالم؛ فیچر آزمایشی fail-closed.
4. آیا grant داده per-metric و زمان‌دار باشد؟ پیشنهاد: بله.
5. آیا reminder پیش‌فرض خاموش باشد؟ پیشنهاد: بله و فقط opt-in.
6. آیا OTA وب‌باندل Capacitor وارد scope شود؟ پیشنهاد: بعد از پایدارشدن Feature Flag و با تصمیم امنیتی مستقل.
7. سیاست نگهداری sampleهای سلامت پس از disconnect چیست؟ پیشنهاد: حفظ تا حذف صریح کاربر؛ توقف sync فوری.

## ۱۶. Definition of Done هر قابلیت

یک قابلیت فقط زمانی «انجام‌شده» است که:

- API، mobile و admin مرتبط به دادهٔ واقعی متصل باشند؛ mock به‌عنوان موفقیت حساب نشود.
- happy path و failure/retry/idempotency تست شده باشند.
- مجوز `activeRole` و در صورت staff، grant per-member تست شود.
- privacy، AuditLog، retention و حذف/لغو رضایت مشخص باشند.
- event و KPI با taxonomy نسخه‌دار ثبت شوند.
- حالت loading/empty/error/offline و RTL/شمسی پوشش داده شود.
- Feature Flag، default، rollout و rollback plan مشخص باشند.
- مستند API و migration/backfill به‌روز و contract test سبز باشد.
