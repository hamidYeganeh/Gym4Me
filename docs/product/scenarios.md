# Gym4Me — سناریوهای end-to-end

مرجع تصمیمات: [`decisions.md`](./decisions.md) · ترتیب تکمیل و معیارهای اجرایی: [`cursor-implementation-master-plan.md`](./cursor-implementation-master-plan.md)

---

## S1 — ثبت‌نام و سوئیچ نقش

1. کاربر شماره وارد می‌کند → API کد OTP می‌سازد → کاوه‌نگار ارسال می‌کند.
2. تأیید OTP → کاربر با نقش پیش‌فرض `ATHLETE` ساخته می‌شود → access token با `activeRole: athlete`.
3. کاربر مسیر «مربی شو» را طی می‌کند → `CoachProfile` با `UNSUBMITTED` → مدارک → `PENDING`.
4. ادمین تأیید می‌کند → نقش `COACH` به `roles` اضافه می‌شود → اعلان + SMS.
5. کاربر سوئیچر را می‌زند → `POST /account/auth/switch-role { "role": "coach" }` → سرور عضویت نقش را چک می‌کند → refresh قبلی revoke، جفت‌توکن جدید با `activeRole: coach` → UI فضای مربی.

**خطاها:** نقش ندارد → 403 · حساب مسدود → 403 · reuse refresh → revoke همهٔ نشست‌ها.

---

## S2 — رزرو زمین با زرین‌پال

1. ورزشکار زمین و بازه را انتخاب می‌کند → API با قفل تراکنشی تداخل را چک می‌کند.
2. رزرو `AWAITING_PAYMENT` با TTL ساخته می‌شود؛ ظرفیت hold می‌شود.
3. کد تخفیف → محاسبهٔ تقسیم مبلغ → `Payment(PENDING)` → authority زرین‌پال → redirect.
4. callback → verify سمت سرور → `Payment(PAID)` → رزرو `CONFIRMED` → Ledger (کاربر/درگاه بدهکار؛ باشگاه، کمیسیون، مالیات بستانکار) → اعلان.
5. روز جلسه: پذیرش → `CHECKED_IN` → پایان → `COMPLETED`.

**شاخه‌ها:** پرداخت ناموفق یا TTL → `CANCELLED` و آزادسازی hold · عدم حضور → `NO_SHOW` · verify تکراری → idempotent.

---

## S3 — لغو و بازپرداخت

1. ورزشکار لغو می‌زند → `CancellationPolicy` با فاصلهٔ زمانی سنجیده می‌شود.
2. مشمول بازپرداخت → `REFUND_REQUESTED` + `Refund(pending)`.
3. مسیر A: کیف پول (آنی + Ledger reversal). مسیر B: بانکی → تأیید ادمین → `REFUNDED`.
4. رزرو دوره‌ای: «فقط این جلسه» یا «از این به بعد»؛ هر occurrence مستقل settle می‌شود.

**اختلاف:** حساب معلق در Ledger تا داوری ادمین.

---

## S4 — جلسه خصوصی مربی (آنلاین)

1. انتخاب خدمت آنلاین و اسلات آزاد (`CoachAvailability`).
2. رزرو idempotent با `PENDING` و مهلت تأیید ساخته می‌شود؛ ظرفیت hold است.
3. مربی تأیید می‌کند → رزرو پولی `AWAITING_PAYMENT` با TTL پرداخت، رزرو رایگان `CONFIRMED`؛ رد یا انقضای approval ظرفیت را آزاد می‌کند.
4. پرداخت رزرو پولی → `CONFIRMED` → لینک جلسه در اعلان؛ انقضای پرداخت نیز hold را آزاد می‌کند.
5. پایان → `COMPLETED` → سهم مربی در Ledger → امتیاز ورزشکار.

---

## S5 — رزرو همراه مربی

1. ورزشکار سانس را رزرو و «همراه مربی» را فعال می‌کند.
2. سیستم `CoachClubAffiliation` را چک می‌کند؛ در غیر این صورت قانون مهمان-مربی باشگاه.
3. مربی به‌عنوان attendee ثبت و در تقویمش block می‌شود؛ پذیرش هر دو را check-in می‌کند.

---

## S6 — خرید و مصرف عضویت باشگاه

1. باشگاه‌دار پلن می‌سازد (مثلاً ۱۲ جلسه صبح، شعبهٔ مرکزی).
2. ورزشکار می‌خرد → پرداخت → `ClubMembership` با اعتبار جلسات.
3. هر ورود: validate سانس/شعبه/تاریخ → `MembershipCheckIn` → کسر جلسه.
4. اتمام/انقضا → `expired` → اعلان تمدید.

**شاخه‌ها:** چندشعبه‌ای · فریز عضویت با لاگ owner.

---

## S7 — برنامه تمرینی و پایبندی

1. پذیرش شاگرد → برنامهٔ چندهفته‌ای (هفته → روز → جلسه → حرکت).
2. حرکت اختصاصی مربی تا تأیید ادمین فقط برای شاگردان خودش.
3. ورزشکار ست‌ها را لاگ می‌کند → درصد پایبندی.
4. مربی بازخورد می‌دهد؛ ویرایش روزهای گذشته ممنوع (نسخه‌بندی).

---

## S8 — حریم خصوصی متریک

1. ثبت وزن/عکس — پیش‌فرض `PRIVATE`.
2. اشتراک با مربی → `COACH_ONLY`؛ فقط رابطهٔ فعال `CoachStudent`.
3. قطع رابطه → قطع دسترسی در query-time.
4. پست دستاورد فقط داده‌ای را نشان می‌دهد که سطحش اجازه می‌دهد.

---

## S9 — پرسنل و مجوزها

1. باشگاه‌دار پذیرش با preset محدود اضافه می‌کند.
2. درخواست `finance.read` → 403 و UI مخفی.
3. ویرایش مجوز → `AuditLog` + refresh اجباری نشست پرسنل.

---

## S10 — impersonation ادمین

1. ادمین دلیل اجباری وارد می‌کند → `ImpersonationSession`.
2. توکن با scope محدود؛ بنر «به‌جای X هستید».
3. همهٔ اقدامات با `impersonationId` در AuditLog → پایان → `endedAt`.

---

## S11 — تسویه دوره‌ای

1. cron پایان دوره → جمع Ledger → `Settlement(pending)`.
2. ادمین واریز IBAN → `paid` → SMS + گزارش.
3. اختلاف → `disputed`؛ اصلاح فقط با entry جدید (هرگز ویرایش رکورد قبلی).

---

## S12 — اشتراک پلتفرم و enforcement

1. مربی پلن پایه (`maxStudents: 20`) → شاگرد ۲۱ → خطای limit + CTA ارتقا.
2. ارتقا → زرین‌پال → `PlatformSubscription` جدید.
3. انقضا → grace → downgrade؛ داده حذف نمی‌شود، قابلیت‌ها read-only.

---

## S13 — فروش حضوری عضویت و بستن صندوق

1. پذیرش عضو را با موبایل پیدا/ایجاد می‌کند یا CSV را ابتدا dry-run و سپس با batch idempotent وارد می‌کند؛ ردیف تکراری skip و نتیجهٔ هر ردیف گزارش می‌شود.
2. پلن، شعبه و تاریخ شروع را انتخاب می‌کند؛ قیمت نهایی و قوانین نمایش داده می‌شوند.
3. پرداخت نقد/کارت‌خوان/کارت‌به‌کارت یا ترکیبی با reference ثبت می‌شود؛ در حالت ترکیبی جمع tenderها باید دقیقاً برابر مبلغ وصول‌شده باشد.
4. `ClubMembership` فعال می‌شود؛ تراکنش مالی با channel، اپراتور واقعی (مالک/کارمند) و Ledger ثبت می‌شود؛ مبلغ باقیمانده به Debt مرتبط با عضویت تبدیل می‌شود.
5. عضو رسید و در صورت داشتن حساب، SMS/deep link عضویت را دریافت می‌کند.
6. پایان شیفت، پذیرش مبالغ مورد انتظار را با صندوق و رسید کارت‌خوان تطبیق می‌دهد.

**خطاها:** پرداخت جزئی → بدهی/قسط با سررسید · لغو ثبت اشتباه → reversal، نه حذف · مغایرت صندوق → ثبت دلیل و تأیید مدیر.

---

## S14 — صف انتظار و offer ظرفیت

1. ظرفیت کلاس/سانس پر است؛ ورزشکار با اولویت و تعداد نفرات وارد waitlist می‌شود.
2. لغو رزرو یا افزایش ظرفیت → سیستم اولین افراد واجد شرایط را انتخاب می‌کند.
3. offer زمان‌دار با push و در صورت اهمیت SMS ارسال می‌شود.
4. پذیرش offer → hold ظرفیت و مسیر پرداخت؛ رد/انقضا → نفر بعد.

**قواعد:** هر offer idempotent است · یک نفر چند جایگاه فعال نمی‌گیرد · policy باشگاه ترتیب FIFO یا اولویت عضو را تعیین می‌کند.

---

## S15 — تمدید و جلوگیری از ریزش

1. eventهای check-in و عضویت، segmentهای «اعتبار کم»، «انقضای نزدیک» و «عدم مراجعه» را به‌روزرسانی می‌کنند.
2. journey طبق consent، quiet hours و frequency cap پیام مناسب می‌فرستد.
3. CTA با deep link به تمدید همان پلن یا گزینه‌های مجاز باز می‌شود.
4. پرداخت موفق → `membership_renewed` و خروج از journey؛ عدم خرید → حداکثر طبق playbook پیگیری می‌شود.
5. dashboard باشگاه conversion و holdout را گزارش می‌کند.

**Guardrail:** داده سلامت/KYC وارد segment بازاریابی نمی‌شود؛ تخفیف پیش‌فرض نیست؛ opt-out فوراً اعمال می‌شود.

---

## S16 — دعوت و پاداش دوطرفه

1. دعوت‌کننده لینک `/r/{code}` را به اشتراک می‌گذارد؛ first-touch ذخیره می‌شود.
2. کاربر جدید ثبت‌نام می‌کند؛ ارتباط referral write-once و ضد self-referral بررسی می‌شود.
3. پس از اولین پرداخت یا check-in واجد شرایط، `referral_qualified` ثبت می‌شود.
4. reward نسخه‌دار برای هر دو طرف صادر و در Ledger ثبت می‌شود.
5. refund/fraud → clawback با entry معکوس؛ رکورد قبلی حذف یا ویرایش نمی‌شود.

**خطاها:** event تکراری → بدون reward دوم · device/payment مشترک مشکوک → review · کمپین منقضی → دلیل رد در UI.

---

## S17 — check-in در شبکه ضعیف

1. مدیر دستگاه را provision می‌کند؛ secret فقط یک‌بار نمایش و فقط hash آن ذخیره می‌شود، و در صورت نیاز قابل rotation است.
2. در حالت آنلاین دستگاه event را با `x-gym4me-device-key` می‌فرستد؛ همان eligibility رزرو/عضویت بررسی و event id به idempotency key تبدیل می‌شود.
3. برای قطعی شبکه، دستگاه snapshot امضاشده و کوتاه‌عمر مجوزهای check-in را نگه می‌دارد؛ QR و رکورد محلی با device، زمان و nonce ثبت می‌شوند.
4. پس از اتصال، رکوردها به‌ترتیب sync و سمت سرور validate می‌شوند.
5. مصرف تکراری یا عضویت نامعتبر به صف بررسی می‌رود؛ سابقهٔ محلی حذف نمی‌شود.

**محدودیت:** عملیات مالی و ایجاد عضویت جدید آفلاین انجام نمی‌شوند؛ سقف زمان/تعداد آفلاین per-device اجباری است.

---

## S18 — ثبت روزانهٔ فعالیت و سلامت

1. ورزشکار از خانه یا صفحهٔ متریک «ثبت فعالیت» را باز می‌کند و آب، وزن، قدم، پیاده‌روی یا خواب را انتخاب می‌کند.
2. مقدار، زمان، واحد canonical و یادداشت اختیاری ثبت می‌شوند؛ privacy پیش‌فرض `PRIVATE` است.
3. API validation نوع متریک را اعمال و sample را با `clientMutationId` idempotent ذخیره می‌کند.
4. خلاصهٔ همان روز طبق aggregation تعریف‌شده در `MetricType` به‌روزرسانی و تاریخچه با تقویم شمسی نمایش داده می‌شود.
5. اگر ورزشکار grant فعال داده باشد، مربی فقط scopeهای مجاز را در درخواست بعدی می‌بیند.

**شبکه ضعیف:** رکورد در صف محلی `pending` می‌ماند و پس از اتصال sync می‌شود؛ retry نباید duplicate بسازد.

**خطاها:** مقدار خارج از بازه → خطای قابل اصلاح · اختلاف منبع دستی/دستگاه → هر دو source حفظ می‌شوند · revoke مربی → دسترسی query-time فوراً قطع می‌شود.

---

## S19 — اتصال Apple Health / Health Connect

1. flag مربوط به platform و app version بررسی می‌شود؛ اپ قبل از permission هدف و نوع داده را توضیح می‌دهد.
2. ورزشکار نوع داده‌های مجاز را انتخاب می‌کند؛ `HealthSyncState` با status متناسب ذخیره می‌شود.
3. اپ بازهٔ محدود اولیه را می‌خواند و batch دارای `sourceRecordId` می‌فرستد.
4. سرور sampleهای تکراری را dedupe و نتیجهٔ created/deduplicated/rejected را per batch برمی‌گرداند.
5. sync بعدی incremental و cursor-based است؛ disconnect فوراً خواندن دادهٔ جدید را متوقف می‌کند.

**شاخه‌ها:** permission جزئی → فقط همان metricها sync · provider unavailable → ثبت دستی فعال می‌ماند · disconnect → دادهٔ قبلی تا حذف صریح ورزشکار حفظ می‌شود.

## S20 — rollout و سازگاری نسخهٔ اپ

1. اپ Next.js + Capacitor در cold start آخرین config سالم را از cache می‌خواند.
2. `GET /api/app-config/bootstrap` با platform، appVersion، build، channel و installationId فراخوانی می‌شود.
3. سرور release policy و Feature Flagها را resolve می‌کند؛ cohort rollout برای installation ثابت می‌ماند.
4. اپ response را schema-validate می‌کند و فقط config کامل و معتبر را جایگزین cache می‌کند.
5. feature آماده در navigation بعدی فعال می‌شود و exposure/error per cohort ثبت می‌گردد.

**شاخه‌ها:** timeout/manifest نامعتبر → last-known-good یا bundled default · نسخه زیر minimum → صفحهٔ blocking update · افزایش خطا → ادمین kill switch/rollback می‌زند.

**محدودیت:** Feature Flag فقط کد از قبل نصب‌شده را فعال می‌کند و هیچ authorization یا permission بومی جدیدی ایجاد نمی‌کند.

---

## S21 — feed داینامیک و شخصی‌شدهٔ اکتشاف

1. ادمین سکشن‌های typed صفحهٔ `discovery_home` را مرتب، targeting علایق و منبع داده را تنظیم و draft را با context مهمان یا ورزشکار پیش‌نمایش می‌کند.
2. publish یک revision تغییرناپذیر می‌سازد؛ renderer ناشناخته، لینک ناامن، شناسهٔ تکراری یا ترکیب strategy/type نامعتبر رد می‌شود.
3. موبایل صفحهٔ اول را با `page_size=8` می‌گیرد؛ سرور revision، نقش فعال، `AthleteProfile.sportIds/goalKeys` و location را به یک feed session کوتاه‌عمر متصل می‌کند.
4. فقط هشت سکشن همان صفحه resolve می‌شوند؛ منابع شامل باشگاه، مربی، کلاس، فضا، سانس، تجهیزات، پلن عضویت، پیشنهاد قابل رزرو و امکانات projection کارت دارند و سکشن خالی طبق `hide/show_empty/fallback` رفتار می‌کند.
5. پیشنهاد قابل رزرو فقط occurrence آینده‌ای را نمایش می‌دهد که مسدود/لغوشده نیست و شمارندهٔ ظرفیت اتمیک آن `remaining > 0` است؛ سانس امروز/فردا نیز با timezone تهران resolve می‌شود.
6. نزدیک انتهای اسکرول، موبایل صفحهٔ بعد را با `feed_token` می‌گیرد؛ ترتیب و targeting تا refresh ثابت می‌مانند.

**شاخه‌ها:** مهمان → feed عمومی · `activeRole` غیرورزشکار → بدون علایق AthleteProfile · token منقضی/متعلق به کاربر دیگر → restart از صفحهٔ اول · تغییر publish یا علایق وسط اسکرول → feed فعلی ثابت و refresh بعدی نسخهٔ تازه.

**محدودیت:** ادمین فقط rendererهای از قبل نصب‌شده در موبایل را ترکیب می‌کند؛ دادهٔ سلامت و متریک خصوصی وارد recommendation نمی‌شود.
